# Chainlink Reference Price Model

This document describes how Aries separates **signal data** (Binance) from
**trading/reference data** (Polymarket's official Chainlink feeds), why that
separation is required for accuracy, and the research basis for each component.

## 1. Resolution mechanics (verified against the live API)

BTC 5-minute markets state in their description:

> This market will resolve to "Up" if the time-weighted average price (TWAP) of
> Bitcoin, generated by Chainlink, of the time range specified in the title is
> greater than or equal to the price at the beginning of that range.

Key facts measured from Polymarket's official endpoints:

- Resolution source: Chainlink `BTC/USD TWAP 60s` data stream
  (`cryptoMarketConfig: btc-5m-twap-60`, `twapLookbackSeconds: 60`).
- The **price to beat** is the Chainlink price at window open, exposed as
  `openPrice` by `GET /api/crypto/crypto-price` (UI contract: ISO-8601 UTC
  `eventStartTime`/`endDate`, `variant=fiveminute`, `twapEnabled=true`,
  `twapLookbackSeconds=60`). Unix-second timestamps return coarser hourly
  data and must not be used.
- `closePrice` (the final resolution TWAP) is only published after the window
  completes (`completed: true`).
- The live Chainlink sample series is exposed by `GET /api/crypto/price-history`
  with the same parameters: one official sample every ~4 seconds, starting
  exactly at window open. The first sample equals `openPrice`.
- Outcome rule: `TWAP >= price to beat` resolves **Up** (ties go Up).

Binance BTCUSDT is a different venue/quote asset than the Chainlink BTC/USD
aggregate. A measured divergence of $45–$67 (7–10 bps) between the two feeds
is common, which is enough to flip which side of the target the "current
price" is on. Any system that compares Binance spot against the Chainlink
price to beat trades against a phantom reference.

## 2. Architecture: signals vs reference

```
Binance WS (high frequency)          Polymarket official endpoints
  MA pressure, slopes, velocity        openPrice  -> price to beat (target)
  order-book imbalance, OFI/CVD        price-history samples -> live Chainlink
  volume spike, microstructure                     price + TWAP accumulation
            |                                     |
            v                                     v
   basis anchor (Chainlink - Binance)      reference price hierarchy
            |                                     |
            +----> anchored signal levels ------->+---> distance, actual side,
                                                     probability, entry gates
```

- **Binance is only a signal feed.** It predicts direction (fast MAs, slopes,
  book imbalance, order flow). It is never compared directly to the target.
- **Chainlink is the trading reference.** Distance-from-target, the
  actual-side determination, persistence, and entry gates all use the
  reference price hierarchy below.
- Orders are still executed against Polymarket CLOB quotes (UP/DOWN asks and
  bids), as before.

## 3. Components and research basis

### 3.1 Reference price hierarchy

1. `chainlink` — the freshest official Chainlink sample (max age configurable,
   default 15s; samples arrive every ~4s).
2. `binance_anchored` — Binance price shifted by the last estimated basis, used
   between Chainlink samples or when the feed is briefly stale.
3. `binance_raw` — unanchored Binance; entries are blocked in this state by
   default (`chainlink_reference.require_for_entry: true`).

Blocking trades when the reference is not Chainlink-grade is a
**selective prediction / abstention** rule: restricting predictions to
high-certainty inputs improves realized accuracy at the cost of coverage
(Chow, 1970; El-Yaniv & Wiener, 2010).

### 3.2 Basis anchoring (lead–lag alignment)

Chainlink aggregates multiple exchanges at lower update frequency; Binance
typically leads it. The basis `b = P_chainlink - P_binance` is estimated from
paired observations with an EMA (default alpha 0.3) plus an outlier cap
(default 50 bps) so fast moves do not corrupt the anchor. Between official
samples, the bot uses `P_binance + b` as its estimate of the current Chainlink
level.

This is standard cross-venue price alignment. Related literature: Hasbrouck
(1995) on information shares across venues; Glosten & Harris (1988) on
transaction-level price components; Cont, Kukanov & Stoikov (2014) on order
book event impacts that justify keeping Binance microstructure as the fast
signal while anchoring its level to the resolution venue.

### 3.3 TWAP lock-in diagnostic

Resolution uses the TWAP over the final 60 seconds of the window. Aries keeps
every official sample and computes the step-function time-weighted average
already accumulated inside that lookback:

- `accumulated_seconds` / `locked_fraction` — how much of the TWAP is fixed.
- `twap_so_far` — running TWAP value versus the price to beat.

This is the same accumulation structure as Asian-option fixing: once the
lookback window is mostly filled, the outcome is nearly determined regardless
of the spot price. Today this state is diagnostic (terminal, dashboard,
decision logs). It is deliberately not yet an entry input because Aries'
default entry window (8–45s after open) finishes before the TWAP lookback
starts; it becomes decision-relevant for late adds/exits and for validating
settlement.

### 3.4 Settlement

Settled windows prefer the official pair (`openPrice`, `closePrice`) with the
true rule `close >= open -> UP` (`settled_from_polymarket_chainlink_twap`).
Binance closes remain only an availability fallback
(`settled_from_binance_close_near_window_end`).

## 4. Validation protocol

- Paper mode only while validating; compare `reference_source` distributions
  (expect mostly `chainlink`, some `binance_anchored`, ~never `binance_raw`
  entries).
- Track Brier score / calibration of `p_up` against settled outcomes via the
  existing optimizer; the distance feature is now measured against the real
  resolution reference, which is a precondition for meaningful calibration
  (Niculescu-Mizil & Caruana, 2005).
- Walk-forward: the optimizer already splits history into train/validation
  segments; keep that discipline for any weight change.
- Monitor `price_basis`: a slowly drifting basis is normal; abrupt persistent
  jumps suggest feed issues, not strategy signal.

## 5. Roadmap (proven next steps, not yet implemented)

1. **Probability calibration layer** — fit Platt/isotonic regression on
   settled `(p_up, outcome)` pairs per timing bucket and apply it before edge
   computation; gate on minimum calibration samples (the optimizer already
   reports Brier and calibration status).
2. **TWAP-aware late-window decisions** — use `locked_fraction` to gate or
   size late same-side adds and exits once entries move later in the window.
3. **Volatility-scaled distance** — normalize distance by realized 60s
   volatility (already computed) so the distance score adapts to regime.
4. **Feature-level lead–lag** — replace the scalar basis with a short-horizon
   predictive model of the Chainlink increment from Binance OFI/velocity
   (Cont et al., 2014 style), validated strictly out-of-sample.

## Settings

```yaml
polymarket:
  crypto_price_url: https://polymarket.com/api/crypto/crypto-price
  crypto_price_history_url: https://polymarket.com/api/crypto/price-history
  crypto_price_symbol: BTC
  crypto_price_variant: fiveminute
  crypto_price_twap_enabled: true
  crypto_price_twap_lookback_seconds: 60

chainlink_reference:
  enabled: true
  refresh_seconds: 2
  max_price_age_seconds: 15
  require_for_entry: true
  basis_ema_alpha: 0.3
  max_abs_basis_bps: 50
```
